## 二、硬件约束（决定系统选型的硬条件）

`/boot/firmware/config.txt` 中的关键项：

```ini
dtoverlay=vc4-kms-v3d          # KMS 显示驱动
dtoverlay=waveshare-35dpi-4b   # 屏幕（Pi 4B）
dtoverlay=waveshare-35dpi-5b   # 屏幕（Pi 5）
dtoverlay=dwc2,dr_mode=host    # 内置键盘走 USB OTG，必须有这行
```

| 约束 | 后果 |
|---|---|
| 屏幕依赖 **vc4-kms-v3d** + `waveshare-35dpi-*` overlay | 这些 `.dtbo` **只随树莓派官方内核包分发**。用 mainline 内核的发行版（Alpine、通用 Debian/Ubuntu arm64、Armbian）**没有这些 overlay，屏不亮** |
| 键盘依赖 **dwc2 host 模式** | 同样是树莓派 firmware/config.txt 的特性 |
| 屏幕仅 **640×480**、**没有鼠标** | 控制台字号与 TUI 工具选型都要按这个约束挑 |

> **结论**：**Raspberry Pi OS Lite (64-bit)** 是唯一"零风险"的选择——
> 它带官方内核与全部 overlay，只是不装桌面。换其他发行版等于放弃屏幕与键盘。

## 三、代理工具：xray-knife（已实测）

### 3.1 为什么选它

| 能力 | 说明 |
|---|---|
| **订阅管理** | `subs add/fetch/show/remove`，配置进 SQLite（`~/.xray-knife/xray-knife.db`），同时导出 `configs.txt` |
| **双核** | 按协议自动选 xray-core 或 sing-box；我们用到的全是 `vless`，走 xray |
| **节点测速** | `http -f configs.txt` 并发测延迟/可用性，可用节点写入 `valid.txt`（按速度排序）|
| **本地代理 + 自动轮换** | `proxy inbound`，可定时轮换、健康检查、失败拉黑 |
| **aarch64 预编译** | `Xray-knife-linux-arm64-v8a.zip`（21 MB 压缩 / 61 MB 解压，**静态链接、stripped**）|
| **不依赖 Go** | 静态二进制，直接跑 |

### 3.2 实测记录（本机 aarch64，2026-10-12）

```
① 下载      Xray-knife-linux-arm64-v8a.zip → v11.3.0（2026-09-28）
             file: ELF 64-bit LSB executable, ARM aarch64, statically linked, stripped

② 订阅      从 v2rayN 的 SQLite 里取出订阅（备注 pasarguard）
            xray-knife subs add --url "<订阅地址>" --remark "pasarguard"
            xray-knife subs fetch --all
            → fetched 5 links, saved 5 configs（全部 vless）

③ 测速      xray-knife http -f configs.txt
            → Found 4 working configs (out of 5)，1 个 http-timeout

④ 本地代理  xray-knife proxy inbound -f valid.txt --port 9999 --inbound socks
            → 出口 IP 207.57.127.15，Hong Kong / AS139659 LUCIDACLOUD
            → google 204: HTTP 204
            → ALL_PROXY 方式与 git ls-remote 均成功
```

### 3.3 ⚠️ 两个必须知道的坑

**坑 1：`--inbound` 默认是 `vless`，不是 socks**

```bash
# ❌ 这样起的不是 SOCKS 代理，curl -x socks5h:// 会一直握手失败
xray-knife proxy inbound -f valid.txt --port 9999
# ✅ 必须显式指定
xray-knife proxy inbound -f valid.txt --port 9999 --inbound socks
```

**坑 2：SOCKS 入站会生成随机用户名/密码，且只在日志里打印**

```
==========INBOUND==========
Protocol: socks
Address: 127.0.0.1   Port: 9999
Username: <随机>
Password: <随机>
Link: socks://<base64>@127.0.0.1:9999#Listener
============================
```

客户端必须带凭据，否则服务端回 `0x05 0xFF`（拒绝所有方法），
curl 报 `No authentication method was acceptable`：

```bash
curl -x "socks5h://<user>:<pass>@127.0.0.1:9999" https://example.com
export ALL_PROXY="socks5h://<user>:<pass>@127.0.0.1:9999"
```

> **排查这类问题的方法**：别只看 curl 的报错，直接做原始 SOCKS5 握手看服务端选哪个方法——
> `b"\x05\x01\x00"`（只提供"无认证"）→ 回 `05ff` 说明它要求认证；
> 提供 `[0x00,0x02]` → 回 `0502` 即确认为用户名/密码认证。

### 3.4 常用命令

```bash
xray-knife subs add --url "<订阅地址>" --remark "名称"
xray-knife subs fetch --all
xray-knife http -f configs.txt                 # 测可用性，结果写入 valid.txt
xray-knife proxy inbound -f valid.txt --port 9999 --inbound socks --rotate 600
xray-knife proxy inbound --port 9999 --rotate 300   # 不带 -f 则用数据库里的池子
xray-knife parse -c "vless://..." --json > x.json  # 生成标准 xray JSON（可给官方 xray 用）
xray-knife proxy tun --bind eth0               # 全机 TUN 接管（需 root）
xray-knife proxy app -c "vless://..."          # 只代理单个进程（network namespace，需 root）
```

其它值得知道的：`dpi`（找能过 DPI 的分片参数）、`cfscanner`（扫 Cloudflare 优选 IP）、
`net`（TCP 诊断）、`db`（库维护/备份）。

## 五、OS 选型（调研完成，含一处重要更正）

### 5.1 ❗ 更正：厂商 overlay **不在任何包里**（实测确认）

我原先以为 `waveshare-35dpi-*.dtbo` 随树莓派官方内核分发 —— **错了**。实测：

```
dpkg -S /boot/firmware/overlays/waveshare-35dpi-4b.dtbo  →  ❌ 无任何包拥有它
官方内核包 linux-image-6.18.50+rpt-rpi-v8 内 dtbo 数量    →  383 个
  其中 vc4-kms-v3d.dtbo                                   →  ✅ 有
  其中 waveshare-35dpi-*                                  →  ❌ 没有
```

**含义（直接影响重装清单）**：
- 这两个 `.dtbo` 是**手工放进去的文件**，不属于任何包 → **`apt upgrade` 不会动它，但重装/换卡一定会丢**
- 官方取回方式：Waveshare [PocketTerm35 软件配置文档](https://docs.waveshare.net/PocketTerm35/Software-Guide/) 中的
  [3.5HDMI_E_DTBO.zip](https://www.waveshare.net/w/upload/d/d0/3.5HDMI_E_DTBO.zip)
  （官方原文："点击下载 PocketTerm35 DTBO 文件并解压，将解压后的 .dtbo 文件复制到 overlays 目录"）。
  该 zip 本仓库另有归档：`pocketterm35/downloads/3.5HDMI_E_DTBO.zip`
- **已从本机抽取并校验可用的副本**（合法 FDT `d00dfeed`），放在：
  `pocketterm35/docs/dtbo-working-backup/`（`waveshare-35dpi-3b/4b/5b.dtbo` + `config.txt.working` + `cmdline.txt.working`）
- ⚠️ 这些厂商文件**许可不明**，已加入 `.gitignore`，**不要随仓库分发**；重装时从本机这份拷贝回去即可

### 5.2 更正：真正的分界线不是"官方内核 vs mainline"

树莓派固件 `start.elf` 会在把 DTB 交给内核**之前**就把 overlay 合并进去（RPi 官方 device-tree.md）。
所以只要发行版**使用 start.elf 这套固件加载链**，overlay 就与内核来源关系不大 ——
真正的前提是**内核里编了 VC4/V3D 驱动**。实测本机内核：

```
CONFIG_DRM_VC4=m        CONFIG_DRM_V3D=m         ← 有驱动
CONFIG_FRAMEBUFFER_CONSOLE=y                       ← KMS 下 fbcon 可用
CONFIG_FONT_8x8=y       CONFIG_FONT_8x16=y         ← 只有这两种字体
```

### 5.4 Lite 版现实：它已经很干净

实测镜像清单（`2026-10-06-raspios-trixie-arm64-lite`）：

| 项 | 事实 |
|---|---|
| **X/Wayland/LightDM** | **0 个包** —— Lite 默认就是控制台，不需要 `raspi-config` 里关桌面 |
| 仍在的常驻服务 | `cloud-init`(+`rpi-cloud-init-mods`)、`avahi-daemon`+`libnss-mdns`、`bluez`、`udisks2`、`cron`、`rpi-eeprom` |
| **本来就没有** | `modemmanager`、`accountsservice`、`rsyslog`、`plymouth`、`triggerhappy` |
| **最大的一块可删** | `build-essential` 全家：`gcc-14` **60 MiB** + `cpp-14` 30 + `g++-14` 33 + `libstdc++-14-dev` 22 + `binutils` 9 + `gdb` 16 + `libc6-dev` 10 ≈ **180 MiB** |
| 已带 | `git`❌不带、`rsync`✅、`htop`✅、`vim-tiny`、`console-setup`+`console-setup-linux`（字号设置的关键）|

### 5.5 640×480 控制台可读性（硬约束，必须权衡）

内核**只编了 `FONT_8x16` 和 `FONT_8x8`** → `fbcon=font:TER16x32` 之类**不会生效**（字体没编进去，静默无效）。
大字体只能走用户态：`console-setup` + `setupcon`（内部对每个 VT 调 `setfont`，KMS 下可用）。

| 字体 | 640×480 下的列×行 | 取舍 |
|---|---|---|
| **8×16（默认）** | **80×30** | ✅ **推荐**：保住 80 列，`git diff`/`systemctl status` 不折行；3.5" 屏上字高约 2.3mm，与笔记本控制台物理尺寸相当 |
| 12×24 Terminus | 53×20 | 最好读，但**破坏 80 列**，输出会折行 |
| 10×20 | 64×24 | 折中 |
| 16×32 | 40×15 | 太窄，且内核未编译该字体 |

旋转：Waveshare 文档给的 `video=DPI-1:640x480M@60,rotate=90` 是 Lite 下的支持路径；
注意 **DPI 与 HDMI 必然共用同一个旋转值**。本机当前 `cmdline.txt` **没有** `video=` 参数（方向已由 overlay 决定）。

### 5.6 触摸屏：重装免费得到（实测确认）

本机 `config.txt` 里**没有任何 touch 相关行**，触摸仍然工作 —— 由内核自带 overlay 驱动：

```
/boot/firmware/overlays/goodix.dtbo          ← 内核包自带（383 个之一）
/dev/input/event6  1-005d Goodix Capacitive TouchScreen   ← I2C 0x5d 自动探测
```

**含义**：只要保留 `dtparam=i2c_arm=on`，**重装 Pi OS Lite 后触摸自动可用**，
不需要额外找"触摸 overlay"。（Waveshare 部分文档提到 `waveshare-touch-35dpi`，
但本机实测并不需要它。）

⚠️ 注意 Waveshare FAQ 的一条硬性冲突：触摸走 I2C，**若其它 overlay/外设占用了 GPIO2/GPIO3/GPIO4，
触摸会失效**。所以别乱加 I2C/GPIO overlay。

### 5.8 控制台静音/防黑屏（小屏体感明显）

### 5.10 指针问题（没有鼠标的现实）

方向键（D-pad）对 `tmux` / `htop` / `btop` / `vim` / `nvim` / `nnn` **够用**；
但以下**不够**：`yazi`（**Debian trixie 里根本没打包**，先核实再选）、`ranger`/`mc` 的鼠标拖拽、任何点击目标。

可选对策：
- 在 TUI 里**关掉鼠标**：`yazi` 的 `mouse: false`、`mc --no-mouse`、`set mouse=` in vim
- 装 `gpm`（0.66 MiB）救裸 tty 下的 `vim`/`less`；⚠️ **`gpm` 只服务真实 VT，不服务 `/dev/pts/N`**，在 tmux 里无效
- `wtype`/`ydotool` 属 Wayland/X 工具，**纯控制台系统里无关**，不要放进方案

### 5.11 重装清单（Pi OS Lite）—— 最终操作顺序

1. 烧录 `2026-10-06-raspios-trixie-arm64-lite.img.xz`（用 Imager 时可顺便配好 WiFi/主机名/用户）
2. **补回厂商 overlay**：把 `dtbo-working-backup/*.dtbo` 拷到 `/boot/firmware/overlays/`
3. 编辑 `/boot/firmware/config.txt`，在 `[all]` 段加入：
   ```ini
   dtparam=i2c_arm=on
   dtoverlay=vc4-kms-v3d
   dtoverlay=waveshare-35dpi-4b
   dtoverlay=waveshare-35dpi-5b
   dtoverlay=dwc2,dr_mode=host
   ```
4. （可选）删掉最大的那块：`sudo apt purge build-essential gdb`（约 180 MiB）
5. （可选）屏蔽无用的定时器：`sudo systemctl mask apt-daily.timer apt-daily-upgrade.timer`
6. （可选）不用 Imager 的 cloud-init 就禁用（**disable 而非 purge**，保留首启路径）：
   `sudo systemctl disable --now cloud-init cloud-init-local cloud-config cloud-final`
7. 字号：`sudo dpkg-reconfigure console-setup`，或直接改 `/etc/default/console-setup` 的
   `FONTFACE="Terminus"` / `FONTSIZE="8x16"` 后 `sudo setupcon`
8. 部署 `xray-knife`（见 §三）

> ⚠️ 第 2 步只影响**触摸**（§六已更正：屏靠 HDMI，不靠厂商 overlay）；
> 第 3 步的 `dtoverlay=vc4-kms-v3d` 才是亮屏关键。
> 厂商 dtbo 的官方来源：Waveshare 3.5HDMI_E_DTBO.zip。

## 六、❗重大更正：厂商 dtbo 不是为了"让屏亮"，只为了触摸

反编译厂商 overlay 后，结论与此前完全不同（**这直接放松了换发行版的限制**）：

```
waveshare-35dpi-4b.dtbo (635 字节) 反编译结果：
  fragment@0 → i2c1 上挂一个 goodix,gt911 触摸节点，reg=0x14，中断 GPIO4
  ❌ 没有任何显示参数（无 clock-frequency / hactive / vactive / porch…）

waveshare-35dpi-5b.dtbo (1001 字节)：
  含 0x14 与 0x5d 两个 gt911 触摸节点，同样无显示参数
```

### 6.1 这意味着什么

| 误解（我之前说的） | 事实 |
|---|---|
| "厂商 dtbo 让屏幕工作，删了会黑屏" | ❌ **错**。像素输出走 **HDMI**，由内核自带的 `vc4-kms-v3d` 负责；厂商 dtbo **只提供触摸** |
| "换发行版必须带厂商 overlay" | ⚠️ **只在触摸上成立**，而且还有替代方案（见下） |

**硬件路线**：PocketTerm35 用 mini-HDMI 把画面送到屏板，屏板再做 HDMI→40 针 DPI 的转换。
所以内核把它当 **HDMI 显示器**（`card1-HDMI-A-1 = connected`），而不是 DPI 面板。

### 6.2 触摸有两条路（都能用内核自带 overlay）

| 方案 | 配置 | 说明 |
|---|---|---|
| **A（当前/重装最省事）** | 拷回厂商 `waveshare-35dpi-4b.dtbo` | 厂商 patch 的分支，含 `touchscreen-size-x/y` 与 `touchscreen-x/y-mm`（触摸校准参数）|
| **B（不依赖厂商文件）** | `dtoverlay=goodix,addr=0x5d` | 内核自带 overlay，且**支持 `addr=` 覆盖参数**；用 `goodix,gt9271` 驱动 |

> 方案 B 需要实测确认触摸方向/校准是否正确（厂商 patch 多设了尺寸与物理尺寸参数）。
> **值得做的一次实验**（见 §七）。

### 6.3 内核自带 DPI 方案（备用，当前不需要）

内核确实带通用 DPI overlay，可填完整时序：

```
vc4-kms-dpi-generic.dtbo   → 可覆盖 clock-frequency/hactive/hfp/hsync/hbp/vactive/vfp/vsync/vbp
vc4-kms-dpi-panel.dtbo     → 内置型号: innolux,at056tn53v1 / ontat,yx700wv03 / geekworm,mzp280
vc4-kms-dpi-hyperpixel*.dtbo
```

**但本机走的是 HDMI，用不上这些**。保留此信息仅为将来若改成真正 DPI 接线时参考。

## 七、Arch / Ubuntu Server / 其他：值得换吗

### 7.1 先把"省多少"量化（实测，非估算）

| 项 | 实测值 |
|---|---|
| 停掉整个桌面（lightdm+labwc+fcitx5+pcmanfm+wf-panel）| **释放 100 MB 内存、26 个进程** |
| 停桌面后 | 354 MB / 183 进程（仍有 `tailscaled` 42.8、`wireplumber` 26.3、`NetworkManager` 19.7、`xdg-desktop-portal` 18.9…）|
| 你的内存 | **3795 MB 总量，用 454 MB，可用 3341 MB** |
| 冷启动 51 秒的构成 | `NetworkManager` **14.5s**、`e2scrub`、`rpi-eeprom-update`、`udev-settle` 7.2s、`udisks2` 7.2s、`tailscaled` 5.1s —— **桌面不在关键路径上** |

> ⚠️ 我先前用"各进程 RSS 相加 = 283 MB"估算桌面占用，**方法是错的**：RSS 会把共享内存
> （同一份 libc/GTK/字体映射）在多个进程里重复计数。**以实测差值 100 MB 为准。**

### 7.2 逐个评估

| 候选 | 内核有 VC4/V3D 吗 | 有 `start.elf` overlay 链吗 | 结论 |
|---|---|---|---|
| **Arch Linux ARM (aarch64)** | ✅ 是 —— Arch ARM 的 RPi 内核就是树莓派下游内核，`vc4`/`v3d` 是标配 | ✅ 是（它就用 `config.txt` + `start4.elf`）| **技术上可行**。但：滚动发行版、无厂商文档、AUR 之外没人体检这套屏；**换它不省内存**，只省"包数量" |
| **Ubuntu Server arm64 for Pi** | ✅ `linux-raspi` 是真下游内核 | ✅ 是 | 可行但**最重**：netplan/cloud-init 首启导向，给你带的东西比 Pi OS Lite 更多 |
| **Raspberry Pi OS Lite** | ✅ 原生 | ✅ 原生 | 🏆 **最优**：同一内核、厂商文档覆盖、**默认就是纯控制台**（0 个 X/Wayland 包）|
| **DietPi** | ✅ 同一内核 | ✅ | 🥈 包数约 1/3，但 `dietpi-config` 不认这块屏，要手改 config.txt |
| **Alpine / 通用 Debian arm64** | ❌ **Alpine 内核没编 `CONFIG_DRM_VC4`/`CONFIG_DRM_V3D`** | ❌ 通用 Debian 无该启动链 | 不可行 |

### 7.3 我的判断（诚实版）

**换发行版在你的场景下收益接近零，风险不为零**：

1. **内存不是瓶颈**：3.8 GB 只用了 454 MB。省下 100 MB 毫无意义。
2. **启动慢不是桌面的锅**：51 秒里 `NetworkManager` 占 14.5 秒。
   真正该动的是网络栈与 `cloud-init`，**而且这些在任何发行版上都要调**。
3. **Arch/Ubuntu 都不比 Pi OS Lite 轻**：Arch 的"轻"是包少、不是内存少；
   Ubuntu Server 反而更重。**唯一真正更轻的是 Pi OS Lite（或 DietPi）。**
4. **风险不对称**：你刚经历一次"黑屏但 SSH 正常"，恢复靠的是逐层排查。
   再引入一个与厂商文档不匹配的发行版，等于把已知可用的状态换成未知。

**如果你就是想要一个纯净的 Arch/Ubuntu 体验**（这是完全正当的理由），那没问题——
但请把它当"换口味"，不是"为了轻量"。

## 九、无桌面时按键映射服务该怎么办

实测：无合成器时 `/dev/input/event7`（虚拟鼠标）**仍被创建但没有消费者**，
`pt35-buttonmap` 仍在跑（`mode=mouse`）。此时：

- 内核 **fbcon 认键盘** → 方向键/回车/PageUp 都能滚动控制台，**打字正常**
- **鼠标指针无处显示** → 服务的那部分功能变成空转

**建议**：纯终端方案里**直接停用该服务**，方向键回归方向键，少一个常驻进程：

```bash
sudo systemctl disable --now pt35-buttonmap
```

（除非你还是想要"方向键推指针"配合某个终端里的图形程序——那需要合成器，即不是纯终端了。）

### 10.5 镜像是 tar 不是 img（烧写方式完全不同）

```bash
# 1) 分区：1 GiB FAT32(可启动) + 剩余 ext4
sfdisk /dev/sdX <<'EOF'
label: dos
,1G,c,*
,,83
EOF
mkfs.vfat -F 32 -n BOOT /dev/sdX1
mkfs.ext4 -q -L root /dev/sdX2

# 2) 解包（必须 root，不能用 sudo 之外的降权）
mount /dev/sdX2 /mnt/arch-root
tar --numeric-owner -xpf ArchLinuxARM-rpi-aarch64-latest.tar.gz -C /mnt/arch-root

# 3) ★ 把 /boot 内容整体移到 FAT 分区（不做这步无法启动）
mount /dev/sdX1 /mnt/arch-boot
mv /mnt/arch-root/boot/* /mnt/arch-boot/     # 保留 dtbs/ 目录结构
```

**为什么 `dtbs/` 结构不能压平**：U-Boot 脚本里写死了
`load ... /dtbs/${fdtfile}`，而 `fdtfile=broadcom/bcm2711-rpi-4-b.dtb`，
所以 FAT 分区上必须是 `/dtbs/broadcom/bcm2711-rpi-4-b.dtb`。
（我一开始只 `grep /boot/*.dtb` 没看到，差点误判镜像缺 dtb；
实际它在 `/boot/dtbs/broadcom/` 子目录里。）

### 10.6 Arch ARM 在 Pi 4 上的真相（与 Pi OS 的关键差异）

| 项 | Pi OS | Arch ARM |
|---|---|---|
| 内核 | vendor `linux-rpi 6.18.50` | **mainline `linux-aarch64 7.2.10`**（自带 `vc4.ko`/`v3d.ko`）|
| **dtbo overlay 来源** | **内核包自带（383 个）** | **独立的 `raspberrypi-overlays` 包（370 个，141 KB）** |
| 镜像自带 overlay | — | ❌ **只有 63 个，且全是 freescale/rockchip**，**没有 `vc4-kms-v3d`** |
| vendor 内核可用？ | 是 | ❌ 仓库里只有 `linux-rpi-16k`，明确标注 **"bcm2712/RPi5 ONLY"**，Pi 4 用不了（16K 页）|
| 启动链 | 固件直接加载内核 | **固件 → U-Boot（`boot.scr`）→ `/Image` + `/dtbs/$fdtfile`** |

> ⚠️ **最容易漏的一步**：`config.txt` 写了 `dtoverlay=vc4-kms-v3d`，
> 但它的提供者是 `raspberrypi-overlays` 包。**装机后必须立刻 `pacman -Syu raspberrypi-overlays`**，
> 否则**黑屏但 SSH 正常**——极易误判为硬件故障。
> 该包在 **`alarm`** 仓库（不是 core/extra），`pacman` 默认已启用。

### 10.7 决定性工具：在笔记本上 chroot 进 ARM 系统

这是让整件事变可能的关键手段。ARM 卡插在 x86 笔记本上，也让 `pacman`/`mkinitcpio` 真正跑起来：

```bash
sudo apt-get install -y qemu-user-static binfmt-support   # 注册 binfmt
sudo mount /dev/sda2 /mnt/arch-root
sudo mount /dev/sda1 /mnt/arch-root/boot                   # ★ 必须挂 /boot
sudo install -m755 /usr/bin/qemu-aarch64-static /mnt/arch-root/usr/bin/
for d in dev proc sys run; do sudo mount --bind /$d /mnt/arch-root/$d; done
sudo chroot /mnt/arch-root /bin/bash
# → 现在真的在 aarch64 环境里，pacman/mkinitcpio 都能用
```

**必须处理的 3 个 chroot 陷阱**：
1. **`Landlock is not supported by the kernel`** —— 宿主内核不支持 Landlock，
   pacman 的沙箱会失败。解法：在 `pacman.conf` 的 `[options]` 下加 `DisableSandbox`
2. **`keyring is not writable` / `required key missing`** —— chroot 里密钥环未初始化。
   解法：`pacman-key --init && pacman-key --populate archlinuxarm`
3. **`exists in filesystem` 冲突** —— 手工拷进去的文件 pacman 不认。
   解法：`rm -rf` 掉手工放的目录/文件，让 pacman 干净接管

### 10.9 烧写过程中我的脚本踩的 3 个坑

| # | 现象 | 原因 | 修复 |
|---|---|---|---|
| ① | `cp: cannot create regular file '.../overlays/': Not a directory` | **镜像 `/boot` 里根本没有 `overlays/` 目录**（它由 `raspberrypi-overlays` 包创建），cp 到带尾斜杠的不存在目录即报此错 | 先 `mkdir -p /boot/overlays` |
| ② | `cp: failed to preserve ownership`: Operation not permitted | **FAT32 没有 Unix 权限/属主模型**，`cp -a` 尝试保留属主必然失败并以非 0 退出 | 用普通 `cp` |
| ③ | `FIRST-BOOT-README.txt` 缺失 | 脚本被中断后已写入部分不回滚 | 手工补写；脚本加 `8/8 最终自检` |

> 教训：**给 FAT32 分区拷文件时永远不要用 `cp -a`/`cp -p`。**

### 10.10 首次开机结果：屏幕亮了但键盘不行（2026-10-13）

**结论**：预置的 `config.txt` + 厂商 dtbo **有效**，屏幕正常点亮。

⚠️ **待核实的唯一悬而未决项**：`raspberrypi-overlays` 是否在开机前已安装。
逻辑上这是**必须的**（`dtoverlay=vc4-kms-v3d` 的提供者），但用户报告"正常启动"

  a) 用户已按说明执行了 `pacman -Syu raspberrypi-overlays` → 符合预期
  b) **`vc4-kms-v3d` 在 Pi 4 上其实可以由固件默认设置满足**，

**验证方法**（需要设备联网后执行）：


> **不能想当然**：如果 (b) 成立，说明我在 §11.2 里"不装就黑屏"的断言过强，
> 应当弱化为"必须装，否则 overlay 缺失（是否致命取决于固件默认行为）"。
> 这条要等实测数据回来再改，不要凭推理下结论。

**另一个事实**：新系统**不在网络上**（旧的 WiFi 配置/静态 IP 随卡一起被抹掉），
所以开机后需要先用屏幕+键盘本地配置网络。

### 10.11 另一个隐蔽的坑：Arch ARM 的 /boot 默认不挂载

原镜像的 `/etc/fstab` **只有 `/` 一条**（`/boot` 缺失）。后果：
- 运行时看不到 `/boot/config.txt`（我一开始还在设备上找它，报"No such file"）
- **内核升级后写入 `/boot` 会失败**（或写进根分区的空目录）

修复：给 fstab 加一行（UUID 用 `blkid` 取）：
```
UUID=XXXX-XXXX  /boot  vfat  rw,relatime,fmask=0022,dmask=0022  0  2
```

### 10.12 常用命令（迁移后）

### 11.4 ★ 网络栈的最终方案：**统一到 NetworkManager**

**这是本节最重要的结论。** 反复掉线的根本原因是**两套网络栈抢同一张网卡**：

| 组件 | 真实状态 | 问题 |
|---|---|---|
| `systemd-networkd` | enabled，管 DHCP | 与 NM 抢 wlan0 |
| `NetworkManager` | **实际已接管 wlan0**（我误判为未接管）| 用 DHCP 赢了路由竞争 → 静态 IP 不生效 |
| `wpa_supplicant@wlan0`（独立实例） | enabled，用自己的 `-c` 配置 | 与 NM 启的 wpa_supplicant 实例冲突 |
| `wpa_supplicant`（NM 启的，`-u -s -O /run/wpa_supplicant`） | 后台运行 | 控制目录被我的实例抢占 |

**症状**：静态 IP 不生效、`nmcli dev wifi connect` 报 `Secrets were required`、
`wpa_cli` 能 PING 通但 `list_networks` 为空。

**最终方案（已重启实测通过）**：**只用 NetworkManager**
```bash
# 1. 静态 IP 交给 NM 档案
nmcli connection modify "MyWiFi" \
  ipv4.method manual ipv4.addresses 192.168.1.100/24 \
  ipv4.gateway 192.168.1.1 ipv4.dns "223.5.5.5 192.168.1.1"
nmcli connection up "MyWiFi"

# 2. 停用冲突的两套服务
systemctl disable --now systemd-networkd
systemctl disable --now wpa_supplicant@wlan0
mv /etc/systemd/network/20-wlan-static.network /etc/pt35-wifi/disabled/   # 防复活
```

**重启验证（40 秒恢复）**：
```

NetworkManager         active     ← 唯一管理者
systemd-networkd       inactive
wpa_supplicant@wlan0   inactive
tailscaled / xray-knife-proxy / sshd   active
外网 HTTP 200
```

> **为什么这才是对的**：NM 会自己拉起所需的 wpa_supplicant 实例，不需要也不应该
> 再手动启一个。统一之后 `nmcli` 与 `nmtui` 才真正可用。

### 11.6 wpa_supplicant 控制目录的正确做法（备用知识）

若将来又要用独立 `wpa_supplicant@wlan0`，控制目录**必须与 NM 的分开**：

```ini
# /etc/wpa_supplicant/wpa_supplicant-wlan0.conf
ctrl_interface=/run/wpa_supplicant-wlan0   ← 不能用 /run/wpa_supplicant（NM 占用）
ctrl_interface_group=0
update_config=1
country=CN
```
```ini
# /etc/tmpfiles.d/wpa_supplicant-wlan0.conf（开机预建目录）
d /run/wpa_supplicant-wlan0 0700 root root -
```

**两个从二进制/日志里查证的事实（避免想当然）**：

1. **`-C` 只在没有 `-c` 时生效** —— help 原文：
   `-C = ctrl_interface parameter (only used if -c is not)`。
   所以用 systemd drop-in 传 `-C/run/xxx` 是**无效的**，必须写进配置文件。
2. **`wpa_passphrase` 生成的块含 `#psk="明文"` 注释行**，必须过滤，
   否则明文口令照样落盘（权限 600 也仍是明文）。

### 11.7 ⚠️ 我在恢复过程中的操作失误

**错误**：为了启用 `nmtui`，我先执行了 `systemctl disable --now systemd-networkd`，
然后才尝试用 `nmcli` 创建 WiFi 档案 —— 但 NetworkManager 尚未满足运行条件，
`nmcli` 报 `NetworkManager is not running`，结果**两个网络栈都没了**，设备彻底离线。

**正确顺序**应是：
```bash
systemctl enable --now NetworkManager      # 1. 先让 NM 跑起来
nmcli connection add ...                   # 2. 建好 WiFi 档案
nmcli connection up "<档案>"                # 3. 确认 NM 真能连上（此时 networkd 还在，失败不掉线）
# 4. 确认新通路可用后，才停用旧服务
systemctl disable --now systemd-networkd
```

**教训**：**任何会中断当前连接的操作，必须先建立并验证替代通路，最后才拆除旧通路。**
这条对远程操作任何设备都适用。

## 十三、TUI 乱码的完整排查与解决（kmscon）

### 13.1 两个独立原因（都找到了实证）

**原因 A：没有 UTF-8 locale**

```
LANG=未设置   LC_CTYPE="POSIX"   /etc/locale.conf: LANG=C   locale.gen 已启用项: 空
```
TUI 需要 UTF-8 locale 才能正确编码制表符与中文。

**原因 B（更隐蔽）：控制台字体根本不含制表符**

用 [`scripts/psf-probe.py`](../bin/psf-probe.py) 解析 PSF 字体表，得到**硬数据**：

| 字体 | magic | 含制表符/符号 |
|---|---|---|
| `Lat2-Terminus16`（我先前选的）| `0xb572` ❌ **非 PSF 格式** | **0/44** |
| **`ter-u16n`** | `0x0436` ✅ 真 PSF | **31/44** |
| `default8x16` | `0xb572` ❌ | 0/44 |

### 13.7 ★ xray-knife 的 `SIGILL` 崩溃：**文件损坏，不是 CPU 不兼容**

**症状**：重启后 `xray-knife-proxy` 反复失败，`status=2/INVALIDARGUMENT`：
```
SIGILL: illegal instruction
PC=0xdf7540  m=0  sigcode=1
google.golang.org/grpc/internal/backoff.init()
```

**我最初的错误推断**：看到 `SIGILL` + Pi 4 CPU 特性里没有 `sha1`/`sha2`/`sve`，
就判断是"二进制用了 CPU 不支持的指令"，并去下载 v8/v9/v10 旧版测试。

**真相（用哈希验证得出）**：
```
本机（两次独立下载）: md5 = 1fc76618c4f718577f2bf3fa51e41e3f
Pi 上那份:            md5 = a42a770ba09de4b6ef3411e2f50fa85f   ← 不同
文件大小:             两者都是 61800574 字节   ← 长度相同，内容不同
```

**大小相同、内容不同 = 传输或写入损坏。** 重新上传并校验哈希后，**同一个 v11.3.0 立即正常工作**。

**关键教训（值得单独记住）**：

> `SIGILL` **不一定**是 CPU 不兼容 —— **损坏的机器码同样会触发非法指令异常**。
> 在改方向之前，**先校验文件哈希**（`md5sum`）。这一步只花 10 秒，
> 而我因为跳过它，白折腾了「找旧版本 + 测三个版本 + 怀疑 CPU 特性」一大圈。

**副产物**：过程中还发现旧版本因 **数据库 schema 版本不匹配**而失败
（v11 建的库是 version 6，v8/v9/v10 读不了），说明**降级不是无损的**。

**正确的排查顺序**：
```bash
md5sum /path/to/binary          # 1. 先验证二进制完整性（最便宜的一步）
# 与本机/官方哈希比对；不一致就重新传输并再校验
```

## 十四、PWM 风扇接入与手持散热

**日期**：2026-10-13
**硬件**：三线 PWM 风扇，接线 **pin4=5V、pin6=GND、pin8=GPIO14（控制）**

### 14.1 为什么不能直接用硬件 PWM

GPIO14 **不是硬件 PWM 引脚**（硬件 PWM 仅 GPIO12/13/18/19），所以用软件 PWM overlay：

```ini
# /boot/config.txt  —— 用 pwm-gpio-fan（任意 GPIO 均可）
dtoverlay=pwm-gpio-fan,fan_gpio=14,...
```

**代价**：GPIO14 原是串口控制台（`enable_uart=1`），必须释放它：
```bash
# config.txt
enable_uart=0
# cmdline.txt：移除 console=serial0,115200
```
> 副作用：失去 USB-TTL 串口救砖能力。但 SSH + Tailscale 仍在，可接受。

**验证成功**：
```
pwmchip0: npwm=1                    ← PWM 设备出现
hwmon2: pwmfan                      ← 风扇注册为 hwmon
cooling_device0: type=pwm-fan max_state=4   ← 接入内核温控
```

### 14.2 ★ `pwm1_enable` 的语义（踩坑记录）

| 值 | 含义 |
|---|---|
| 0 | 无调速控制（等价全速）|
| 1 | **手动**模式 |
| **2** | **自动**（交给内核温控）← 正常状态 |

**我犯的错**：手动测试后写 `echo 1 > pwm1_enable` 以为是"恢复自动"，实际是切到手动。
之后看到"风扇不转"就去查原因，**却没先确认温度是否达到启动阈值**（当时 52°C < 55°C 阈值，
停转本来就是正确行为）。这是又一次"先下结论再验证"。

**另一个迷惑现象**：自动模式下写 `pwm1` 会被立即覆盖回 `cur_state` 对应值
（多档位驱动的 thermal handler 强制同步），所以手动测试必须先设 `pwm1_enable=1`。

### 14.3 实测：热地板与频率的关系

满速风扇 + 系统空闲，逐档限制 CPU 频率：

| 频率上限 | 稳定温度 | 相对性能 |
|---|---|---|
| 1500 MHz | 46.3°C | 100% |
| 1000 MHz | 45.3°C | 67% |
| 800 MHz | 45.8°C | 53% |
| **600 MHz** | **45.8°C** | 40% |

**结论：降到 600 MHz 温度也不再下降** → 存在**与 CPU 频率无关的固定热源**
（WiFi 芯片 / USB 控制器 / 供电电路）。**SoC 热地板 ≈ 45–46°C**（室温约 30°C、风扇满速、空闲）。

> **推论**：`arm_freq` 降频对降温的收益很小（1500→1000 只降约 1°C，却损失 33% 性能）。
> 用户最终选择**不降频**，这是合理的。

### 14.4 ★ 负载场景决定一切（关键结论）

用户要求"手持 ≤50°C"。实测分场景：

| 场景 | 温度 | 达标 |
|---|---|---|
| 空闲 | 47.2–48.2°C | ✅ |
| **opencode 实际对话** | **47.2 → 48.2°C** | ✅ |
| 单核突发 20s | 50.6–51.1°C | ⚠️ 压线 |
| **4 核满载 150s** | **61.3°C** | ❌ |

**结论：50°C 在日常使用（终端 + AI 对话）下完全可达**；
只有**持续全核满载**才会到 61°C，而热量累积需要连续 100+ 秒满载。

> **opencode 对话几乎不升温**（47.2→48.2°C）—— 因为 AI 推理在云端，
> 本机只做文本渲染与网络 IO。这是"终端 + AI"场景的天然优势。

**估算的热阻**：ΔT≈31°C / 约 7.4W ≈ **4.2 °C/W**（小风扇 + 机身内部）
→ 要压到 50°C 以下，满载功耗须 < 约 4.8W，即**必须降频**。这是物理限制。

### 14.5 最终风扇曲线（激进版）

```ini
# /boot/config.txt
#   35°C→120(47%)  38°C→180(71%)  41°C→220(86%)  45°C→255(100%)
dtoverlay=pwm-gpio-fan,fan_gpio=14,\
  fan_temp0=35000,fan_temp1=38000,fan_temp2=41000,fan_temp3=45000,\
  fan_temp0_speed=120,fan_temp1_speed=180,fan_temp2_speed=220,fan_temp3_speed=255
```

**效果对比（4 核满载 150s 峰值）**：
```

新曲线（35/38/41/45°C 启动）  : 61.3°C   全程 100%
```

**⚠️ 两个配置项不生效**（发现但未解决，记录备查）：
1. **`fan_temp*_hyst` 被忽略** —— 无论配 2000/3000，读回永远是 `hyst=5000`
2. **`temp_limit=80` 不影响 `trip_point_4`** —— 仍是 110000。
   该参数由固件层处理（降频），不出现在 thermal zone 里

## 十五、极小桌面 + 中文输入（sway + foot + fcitx5）

**日期**：2026-10-13
**背景**：纯终端（kmscon）下无法打中文

### 15.1 为什么纯终端打不了中文（本质原因）

| 方案 | 在 kmscon 下可用？ | 原因 |
|---|---|---|
| fcitx5 / ibus | ❌ | 需要 `DISPLAY` 或 `WAYLAND_DISPLAY`，依赖显示服务器的 **text-input 协议** |
| `uim-fep`（经典终端 IME）| ❌ | `uim` **不在 Arch 官方仓库**（仅 AUR），ALARM 也没有 |
| `loadkeys` 拼音键映射 | ❌ | 组合键是**顺序匹配**：敲 `a` 立即输出 `a`，无法输入两字母音节 `an`，**会破坏正常英文输入** |
| `pyzy` 自建 IME | ⚠️ | 可行（库+词典都在仓库），但要装编译工具链，且终端内注入只有 TIOCSTI 一条路 |

**结论：需要合成器，这是最小代价。** 输入法本质上需要一个提供输入协议的显示服务器。

### 15.2 最小组合（无桌面外壳）

```bash
pacman -S sway foot fcitx5 fcitx5-chinese-addons fcitx5-configtool seatd swaybg
```
**不含**：面板、文件管理器、壁纸、任务栏 —— 只有合成器 + 终端 + 输入法。
`foot` 编译带 `+ime`，通过 wayland `text-input-v3` 接入 fcitx5。

### 15.3 四个必须解决的技术障碍（都实测踩过）

**① seat 管理** —— sway 需要 seatd 或 logind 活动会话
```
No backend was able to open a seat / Failed to load session backend
```
→ `systemctl enable --now seatd`，并设 `LIBSEAT_BACKEND=seatd`

**② 渲染器** —— pixman 缺 allocator
```
[ERROR] [render/allocator/allocator.c:168] Failed to create allocator
```
→ 必须用 `WLR_RENDERER=gles2`（Pi 4 的 vc4 + mesa 支持）

**③ ★ kmscon 抢 DRM master（最关键）** —— 两者不能同时显示
```
connector HDMI-A-1: Atomic commit failed: Permission denied
```
kmscon 占着 tty1 的 DRM master 时，sway **拿不到显示权限**。
→ `zhdesk` 启动前先 `systemctl stop kmsconvt@tty1`，退出后恢复

**④ Xwayland 与 swaybg** —— 可选，消除启动报错

### 15.6 ★ 输入法失效的真正原因（最难排查的一个坑）

**症状**：合成器起来、foot 在跑、fcitx5 进程也在，但**打字没有候选框**。

**根因**：**fcitx5 必须在 sway 的 Wayland 会话内启动，环境里要有 `WAYLAND_DISPLAY`。**
我因为反复从 SSH 手动重启它调试，把它启动在了没有 Wayland 显示的环境里。

**诊断指标（决定性）**：

| 指标 | 坏掉时 | 正常时 |
|---|---|---|
| fcitx5 的 `WAYLAND_DISPLAY` | **缺失** | `wayland-1` |
| `State`（DBus）| **0**（未启用）| **1** |
| `CurrentInputMethod` | **`""`** | `pinyin` |
| 打开的 wayland socket 数 | **0** | ≥1 |

**排查命令**（一次看清环境差异）：
```bash
# 对比 fcitx5 与 foot 的环境 —— 缺 WAYLAND_DISPLAY 就是它
for n in sway foot fcitx5; do
  pid=$(pgrep -x $n | head -1)
  echo "── $n ──"
  tr '\0' '\n' < /proc/$pid/environ | grep -E "WAYLAND_DISPLAY|XDG_SESSION_TYPE"
done

# 用 DBus 查真实状态（State=0 即未接入）
busctl --user call org.fcitx.Fcitx5 /controller \
  org.fcitx.Fcitx.Controller1 State
```

> ⚠️ `CurrentInputMethod` 是 **method 不是 property**。
> 用 `busctl call`（不是 `get-property`），否则报 `Unknown interface`。

**修复**：先等 sway 的 wayland socket 出现，**再**带着 `WAYLAND_DISPLAY` 启动 fcitx5。
`zhdesk` 已实现为轮询等待 + 延迟启动：
```bash
# 轮询等 socket（最多 20 秒）
for _ in $(seq 1 40); do
  sleep 0.5
  WD=$(ls "$XDG_RUNTIME_DIR"/wayland-* 2>/dev/null | grep -v '\.lock$' | head -1)
  [ -n "$WD" ] && break
done
export WAYLAND_DISPLAY=$(basename "$WD")
fcitx5 -d --replace &
busctl --user call org.fcitx.Fcitx5 /controller \
  org.fcitx.Fcitx.Controller1 SetCurrentIM s "pinyin"   # 默认拼音
```

**同时**：从 sway 配置里**移除** `exec fcitx5`。sway 的 `exec` 早于 socket 可用，
可能拿到不完整的环境 —— 这类"看起来合理但实际错的"配置正是坑源。

### 15.7 验证结论

**✅ 已用截图证实可用**（修复后多次复现）：
```
user@device:~$ ni hao              user@device:~$ zhong wen
  1. 你好  2. 👋  3. 你毫 …        1. 中文  2. 中温  3. 钟文 …
```
完整链路：`foot`（text-input）→ `sway` → `fcitx5`（State=1, IM=pinyin）
→ `libime` 拼音 → 中文落入终端。词组联想（`ni hao`→`你好`）与 emoji 候选均正常。

**⚠️ 测试方法的陷阱**（差点误导结论）：
`wtype`（虚拟键盘协议）与 `ydotool`（uinput）都可能**绕过输入法框架**。
用它们测 IME，得到"没候选框"的结论**不可靠**。**真机键盘 + 截图**才是有效验证。

### 15.8 中英文切换（三种含义，别混淆）

| 需求 | 操作 |
|---|---|
| 桌面内**临时**打英文 | 按 **`Shift`**（松开恢复中文）|
| 桌面内**切换**中/英 | **`Ctrl+Space`** 或 `zhime toggle` |
| 桌面**启动就英文** | `ZHDESK_LANG=en zhdesk` |
| **完全回到纯终端** | sway 里 `Super+Shift+e`，或 `pkill -x sway` |

**`zhime` 命令**（新增，已归档 [`scripts/zhime`](../bin/zhime)）：
```bash
zhime          # 查当前输入法与启用状态
zhime en       # 切英文
zhime zh       # 切中文
zhime toggle   # 来回切
```
它在状态异常时会**主动提示诊断**（显示 fcitx5 的 `WAYLAND_DISPLAY` 是否缺失），
把 15.6 节那个坑变成可自查的。

**实测确认**：
```
Ctrl+Space: pinyin → keyboard-us → pinyin   循环正常
截图检查:   终端里**没有** ^@ 等垃圾字符（fcitx5 正确截获了按键）
```

> **设计要点**：kmscon（纯终端）**始终是默认**，`zhdesk` 是**按需**调用。
> 所以"纯英文环境"就是你**什么都不做**时的状态 —— 中文桌面只在主动进入时存在。

## 十六、方法论备忘

### 本轮最重要的教训（值得单独列出）

**「官方模板」的默认值不一定覆盖你的硬件变体。**

`linux-rpi` 的官方 `config8.txt` 里，`dtoverlay=dwc2,dr_mode=host`
**只在 `[cm5]` 段**——因为维护者按 CM5 的硬件写的。而 Pi 4B 的内置键盘
同样需要它。我因为"这是官方模板，应该更权威"而照抄，导致键盘一直不工作。

而**原厂 Pi OS 的 config.txt 里这行在 `[all]` 段、还重复写了两次**——
这是强信号（厂商刻意强调），但被我用"官方模板更权威"的假设覆盖掉了。

> **规则**：当「发行版/上游模板」与「本机实测可用的配置」冲突时，
> **以本机实测为准**。上游模板是针对某个参考硬件的，不是你手上的这块。



1. **在真机上验证，而不是在文档上推断**：`xray-knife` 的 README 只给了 `linux-64` 的下载示例，
   是否支持 aarch64 必须去翻 release 资产列表；能否**运行**则必须真跑。
2. **趁设备还能用时先验证目标方案**：这次是在现有桌面系统上直接跑通了 arm64 二进制与订阅，
   于是重装后只是"复现"，而不是"赌一把"。
3. **报错要挖到协议层**：curl 的 `No authentication method was acceptable` 看不出要用户名密码，
   一次原始 SOCKS5 握手就定位了。
4. **`pkill -f <名字>` 会杀掉自己的 SSH 会话**（命令行里含同样字符串）——
   本次又踩了一次，改用 PID 或 `[x]` 方括号技巧（注意 `pkill` 用 POSIX ERE，方括号可能反而自匹配）。
5. **不要用"各进程 RSS 相加"估算组件占用** —— RSS 会把共享内存重复计数
   （本次算出 283 MB，实测只释放 100 MB）。**要用"停掉它前后的差值"实测。**
6. **反编译二进制资产比读文档可靠**：`dtc -I dtb -O dts` 反编译 635 字节的
   overlay，一眼看出它**只有触摸配置、没有显示参数**，从而推翻了"屏靠厂商 overlay"的假设。
   这类"小文件里到底是什么"的问题，读文档会猜，反编译直接给答案。
7. **改文档时要留意章节编号**：本次插入新节后出现两次编号重复（两个"5.7"、两个"六"），
   靠 `grep -n '^## '` 复查才发现。
