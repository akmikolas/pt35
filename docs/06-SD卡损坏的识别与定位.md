## 一、诊断路径（这次的教训：不要只用一种检测手段）

### 误判 1：以为设备没启动

现象是"没有登录提示 + 网络全断"，我一度判断**系统启动失败**。拆卡检查后发现：

```
fsck.ext4 -n /dev/sda2   → 文件系统完全健康
journalctl -D ... --list-boots → 有 12 次启动记录，最后一次就在当天
journalctl -b 0 | grep NetworkManager
  → /usr/bin/NetworkManager: error while loading shared libraries:
    /usr/lib/libz.so.1: invalid ELF header
```

**系统启动正常，是 NetworkManager 崩了 → 没网络 → 所以"看不到登录提示"（SSH 进不去）**。
"没有登录提示"是**观测方式的问题**，不是启动失败。

### 误判 2：以为只有 6 个文件损坏

我先用**自制的 ELF 头部检测器**扫描，结论是"只有 6 个文件损坏"。
修复后设备仍不正常。最终用 **`pacman -Qkk` 校验和**才发现真实情况：

```
真实损坏（SHA256/Size 不匹配）: 95 个文件
分布在 25 个包里
```

**根本原因：头部检测只能发现"文件头被破坏"的损坏，
而这次的损坏是【头部正常、内容错误】—— 只有校验和能查出来。**

> **规则**：检测文件损坏必须用**校验和**（`pacman -Qkk`），
> 头部魔数检查只能作为快速初筛，**绝不能作为结论**。

### 误判 3：以为 python3 坏了

用 `ctypes.CDLL()` 批量加载库时 python3 段错误，我一度以为 Python 损坏。
实际是**加载到坏库时崩溃**（列表顺序执行到 `libnl` 就死了）。

**修正后逐个独立测试，立刻定位**：
```
💥 libnl-3.so.200          段错误
💥 libnl-genl-3.so.200     段错误
💥 libnl-route-3.so.200    段错误
（其余 15 个库全部 OK）
```

## 二、★ 根因：`libnl` 包损坏 → 连锁反应

```
libnl-3.so.200 损坏
   ├─→ iw 崩溃          （iw 依赖 libnl）
   └─→ wpa_supplicant 无法启动（也依赖 libnl）
          └─→ NetworkManager 拿不到 WiFi
                 └─→ 局域网 + Tailscale 全部失联
```

**一个库坏了，整条网络链路失效。** 而 `libnl` 损坏的文件只有：

```
libnl: /usr/lib/libnl-3.so.200.26.0   ← 就这一个文件
```

## 四、★ 关于 zlib 的 epoch 版本坑

`zlib` 的版本号带 **epoch**：`1:1.3.2-3`。这导致两个问题：

1. **URL 必须编码冒号**：`zlib-1%3A1.3.2-4-aarch64.pkg.tar.xz`（直接写 `1:1.3.2-4` 会 404/403）
2. **仓库列表里 grep 不到**：文件名是 `zlib-1%3A1.3.2-4...`，普通 `zlib-[0-9]` 模式匹配不上

**发现方法**：直接抓仓库目录 HTML，用 URL 编码后的名字匹配。

## 六、根本问题：这张 SD 卡不可信

**这是第 5 次同类损坏**：

| 次序 | 损坏内容 |
|---|---|
| 1 | `libvulkan.so.1`（全零）|
| 2 | `libacl.so.1` + `libutil.so.1` |
| 3 | `libz` + 22 个 gconv + locale |
| 4 | （本次）`libnl` + 95 个文件 |

**卡的标识**：
```
Vendor: Generic     Model: STORAGE DEVICE
内核日志: mmc0: ... SDABC 58.2 GiB
```

**"Generic STORAGE DEVICE" + "SDABC" = 无品牌白牌卡**，写入可靠性存疑。

**证据表明不是文件系统问题**：
- `fsck.ext4 -n` 每次全过

> **结论：软件层面已经防不住了。换正牌卡（SanDisk / Samsung / Kingston A1/A2）
> 是唯一的根治办法。**

# 补充：2026-10-15 第二轮损坏（krb5 崩溃 SSH）

## 一、症状升级：SSH 认证成功后立即断开

```
$ sshpass -e ssh root@192.168.1.100
Authenticated to 192.168.1.100 using "password".    ← 认证成功
Connection to 192.168.1.100 closed by remote host.  ← 立刻断开
```

**所有通道（局域网/Tailscale）+ 所有方式（PTY/直接命令/SFTP）都一样**。
TCP 端口开放、banner 正常、密钥交换完成，**只在认证后崩**。

## 二、根因：`libkrb5.so.3.3` 损坏 → sshd 派生会话时 SIGILL

从卡上日志直接读到崩溃栈：

```
sshd-session[926]: fatal: monitor_child_preauth: preauth child 927 terminated by signal 4
  Stack trace of thread 927:
    #0  libkrb5.so.3 + 0x9e570        ← 信号 4 = SIGILL（非法指令）
    #1  ld-linux-aarch64.so.1 + 0x4a4c
    #2  exit (libc.so.6 + 0x3a54c)
```

**连锁崩溃**（全部 signal 4/ILL）：
```
sshd-auth         ← SSH 认证后断（核心症状）
login             ← 本地登录崩溃
NetworkManager    ← 网络管理崩溃
iptables          ← SEGV (signal 11)
```

> **关键洞察**：即使不用 Kerberos，**PAM 也会加载 `libkrb5`** ——
> 所以它坏了会连累**所有认证路径**（SSH / login / sudo）。

## 四、★ 我写的修复脚本的 5 个 bug（都踩过）

写自动化修复脚本时，这些 bug **每一个都会造成误修**：

| # | bug | 后果 | 修正 |
|---|---|---|---|
| 1 | `os.listdir` 顺序不定 | `libcap` 匹配到 `libcap-ng`，版本校验失败 | 排序 + 精确前缀匹配（`rest[0].isdigit()`）|
| 2 | `%3A` 归一化顺序错 | epoch 版本 `1:1.8.13-1` 被解析成 `13-1` | **先正则解析，后归一化** |
| 3 | `desc` 文件本身损坏 | `attr` 版本读成 None（文件全空字节）| 校验内容 + **回退到目录名解析** |
| 4 | 符号链接被当普通文件 | 会把 `.so` 链替换成普通文件（破坏链接）| 显式 `os.path.islink()` 跳过 |
| 5 | **不做版本校验** | **把 Qt 6.12.0-2 误降级、opencode 误升级** | **严格版本比对**（卡上版本 == 包版本才修）|

> **第 5 条最重要**：`libQt6Core.so.6.12.0` 有 20 字节差异，
> 一度以为损坏。实际是 **GNU build-id**（不同构建的 ID），
> 而卡上是 `6.12.0-2`、仓库是 `6.12.0-3` —— **版本差异，不是损坏**。
> 如果不校验版本就覆盖，会把好文件改坏（降级）。

## 五、★ opencode / bun 的 SIGILL 也是文件损坏

```
旧: opencode 2.0.27  194907208 字节  含 1MB 全零块  pacman SHA256 mismatch
    panic: Illegal instruction   ← bun 内嵌运行时崩溃
新: opencode 2.0.29  195562568 字节  校验通过
    opencode v2.0.29  ✅  端到端模型调用成功
```

**误导性**：`Illegal instruction` 看起来像 **CPU 指令集不兼容**（Pi 4 的
Cortex-A72 确实缺 `lse`/`atomics`），一度怀疑 Bun 要求 ARMv8.1+。
**但实际是文件损坏** —— 卸载重装后立即正常。

> **规则（第二次验证）**：`SIGILL` **不一定**是 CPU 不兼容，
> **损坏的机器码同样会触发**。**先校验文件哈希，再怀疑硬件**。
