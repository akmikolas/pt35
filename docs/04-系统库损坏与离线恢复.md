**症状**：`pacman -S sway foot fcitx5...` 报
```
sed: error while loading shared libraries: /usr/lib/libacl.so.1: invalid ELF header
```
随后 `pacman`、`cp`、`mv`、`sed` 全部失效，`pacman -Q` 连 `glibc`/`coreutils` 都查不到。

---

## 一、诊断过程中的两次误判（教训）

### 误判 1：以为 pacman 数据库损坏

`pacman -Q acl` 输出"不在数据库"，我一度判断**包数据库损坏**。

**真相**：`pacman` 自身依赖 `libacl`，库坏了 → pacman 无法运行 → 所有 `-Q` 查询
都以同样方式失败。**是工具坏了，不是数据坏了。**

**验证方法**：直接看数据库目录，绕开 pacman：
```bash
ls /var/lib/pacman/local/ | wc -l        # 274 个条目
ls /var/lib/pacman/local/ | grep acl     # acl-2.4.0-1 在
```

### 误判 2：第一版扫描报告 202 个"损坏"库

我的检测器把**符号链接**和 **GNU ld 链接脚本**当成损坏：

| 文件 | 前 4 字节 | 真实身份 |
|---|---|---|
| `libm.so`、`libc.so` | `2f2a2047` = `/* G` | **ld 链接脚本**（文本，正常）|
| `libncurses.so`、`libtinfo.so` | `494e5055` = `INPU` | 也是链接脚本 |
| `/usr/lib/systemd/**/*.socket` | `5b556e69` = `[Uni` | systemd 单元文件 |

**正确检测器**必须：
1. `os.path.islink()` 跳过符号链接（并用 `realpath` 去重）
2. 识别 `/* GNU ld script`、`GROUP (`、`INPUT (` 等文本标记
3. 只对"应该是 ELF"的文件（`bin/`、`sbin/`、`.so`）判定

修正后：**1941 个二进制中只有 2 个真损坏**。

## 二、真正的损坏与恢复

### 损坏清单（精确）

```
/usr/lib/libacl.so.1.2.2400   67568 B  head=a4810000...  归属 acl
/usr/lib/libutil.so.1         67672 B  head=bf251c00...  归属 glibc
```
两个文件**大小与正常版本完全相同**，只有前 ~10% 字节被覆写。

### 损坏模式分析（判断是否为硬件故障）

```
[libacl]  长度相同=True  首个差异在第 0 字节  不同字节 7230/67568 (10.7%)
[libutil] 长度相同=True  首个差异在第 0 字节  不同字节 6176/67672 (9.1%)
```

**结论：不是 SD 卡坏块**。理由：
- 若是闪存损坏，差异字节会**分散分布**；实际是**连续覆写文件头部**
- 文件系统 `state: clean`，`dmesg` 中 **0 条** I/O 错误
- 长度完全一致 → 是"部分写入"而非"块丢失"

**真实原因**：中断 pacman 事务 + 未刷盘的写入。**人为操作导致，非介质故障。**

### 恢复步骤（鸡生蛋问题的解法）

难点：`pacman` 依赖损坏的 `libacl`，**无法用 pacman 修 pacman**。

```bash
# 1. 下载包（用 python urllib，不依赖 curl；用 USTC 镜像，4.3MB/s）
#    acl 包 143KB；glibc 包 9.2MB
# 2. 用 python tarfile 提取损坏文件（不依赖 tar/sed/cp）
python3 /tmp/extract-pkg.py /tmp/glibc.pkg.tar.xz /tmp/glibcfix libutil.so
# 3. 原子替换 + 备份 + 校验（不直接覆盖，先验证源文件是合法 ELF）
python3 /tmp/repair-lib.py /tmp/glibcfix/usr/lib/libutil.so.1 /usr/lib/libutil.so.1
# 4. pacman 复活后，用 pacman 正规重装保证数据库一致
pacman -S --noconfirm acl glibc
```

**关键点**：先修 `libacl`（**一个文件**）就足以让 `pacman` 复活，
之后用 pacman 修剩下的 —— 不必手工修所有损坏文件。

### 修复后验证

```
扫描统计: ok=1941  text=186  link=291  skip=281
✅ 未发现损坏的二进制/库

pacman -Qkk glibc    → 1617 total files, 0 altered files
```

## 三、★ 我犯的操作错误（两个高危坑）

### 坑 1：`pacman ... | sed` 导致永久阻塞

我用 `pacman -S ... 2>&1 | sed 's/^/  /'` 的形式执行安装。SSH 会话超时断开后：
- `sed` 消失
- `pacman` 写管道 → **永久阻塞**（`wchan: anon_pipe_read`）
- 它**一直握着 `db.lck`**，导致后续所有安装都报 `unable to lock database`

**正确做法**：长任务输出重定向到**文件**，绝不用管道：
```bash
nohup sh -c "pacman -S ... > /tmp/install.log 2>&1; echo __DONE__ >> /tmp/install.log" &
```

### 坑 2：`pkill -f "pacman -S"` 杀掉自己的 SSH 会话

`pkill -f` 匹配**完整命令行**，而我自己的 SSH 命令行里就含 `pacman -S` 字符串
→ **自杀**。这个坑我在本项目已踩第二次。

**正确做法**：用精确进程名或 PID：
```bash
pkill -x pacman                  # 精确进程名
for pid in $(pgrep -x pacman); do kill -9 "$pid"; done
```

## 四、附带发现

### `command -v X && X --version` 不是可靠的"活着"检测

我用 `sshd --version` 判断 sshd 是否损坏，得到"失败"，于是误判 sshd 坏了。
实际 `sshd` **不支持 `--version`**（参数错误 ≠ 库损坏）。

**正确检测**：
```python
out = (r.stdout + r.stderr).decode()
if "error while loading shared libraries" in out:   # 只看这个特征
    print("库损坏")
```

### 镜像源速度差异巨大

```
USTC       4.3 MB/s     ← 采用
阿里云      100 KB/s
官方 ARM     48 KB/s     ← 原先配置，慢到 1.9 KB/s（同步 extra.db 要几小时）
```
先前"安装卡住"的一部分原因就是**官方源慢**，而非网络故障。
