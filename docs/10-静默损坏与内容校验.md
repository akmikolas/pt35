# 静默损坏：`pacman -Qkk` 查不出的文件内容损坏

> **Note on redaction.** This document was written while debugging a real device.
> All credentials, subscription URLs, hostnames and addresses have been replaced
> with placeholders (`192.168.1.100`, `MyWiFi`, `user@device`, `YOUR_PASSWORD`).

## 现象

一次正常 `reboot` 之后，无线和有线全部不通。

### 直接症状

**正常 `reboot`（没有强制断电）后，无线和有线全部不通。**

- 设备能启动，屏幕正常，但三个地址全不可达
- 有线 `192.168.1.100`、Tailscale —— 全部 `No route to host`
- 用 3.5" 屏 + 内置键盘现场排查，发现 `NetworkManager` 挂了

```bash
$ systemctl status NetworkManager
Main PID: 2782 (code=dumped, signal=ILL)     ← SIGILL
Failed with result 'core-dump'
NRestarts=5  Result=start-limit-hit          ← 重试 5 次触发限制
```

---

## 根因 1（主因）：`libp11-kit.so.0` 内容损坏

### 表现

```
崩溃堆栈（关键在 #0 行）:
  #0  0x0000ffffb9533dd0 n/a (libp11-kit.so.0 + 0x133dd0)   ← ★ 元凶
  #12 0x0000ffffbe5f19b8 g_module_open_full (libgmodule-2.0.so.0 + 0x19b8)
  #11 0x0000ffffbdd74c20 dlopen (libc.so.6 + 0x84c20)
```

NM 通过 GModule `dlopen` 加载 p11-kit → p11-kit 的**构造函数执行时 SIGILL**
→ NM 启动即 core dump → 重试 5 次 → systemd 永久放弃。

### 实际损坏内容

```bash
# 从缓存包提取原版对比
$ cmp -l $T/usr/lib/libp11-kit.so.0.4.11 /usr/lib/libp11-kit.so.0.4.11 | head
   偏移 0x132001: 原版=0x56 当前=0xff
   偏移 0x132002: 原版=0x02 当前=0xff
   ...
   总差异字节数: 14525

# 差异分布（按 4KB 页）
   页 306: 3621 字节
   页 307: 3641 字节
   页 308: 3614 字节
   页 309: 3648 字节
   页 310: 1 字节
```

**从 `0x132001` 起连续 14525 字节（约 3.5 个内存页）被全部填成 `0xFF`。**

> 对比：之前 `xray-knife` 损坏时是填 `0x00`。**这个设备两种填充模式都出现过。**

### ★★★ 最大的陷阱

```bash
$ pacman -Qkk p11-kit
p11-kit: 250 total files, 0 altered files        ← 报"完全正常"！
```

**`pacman -Qkk` 查不出内容损坏。**

原因：pacman 的 mtree 只校验**文件大小 / 权限 / 时间戳**，
**不校验内容 SHA256**。填成 `0xFF` 后文件大小不变 → 校验"通过"。

**唯一可靠的检测方法**：拿缓存包逐字节对比

```bash
T=$(mktemp -d)
tar -xf /var/cache/pacman/pkg/libp11-kit-0.26.5-1-aarch64.pkg.tar.xz -C "$T"
cmp -l "$T/usr/lib/libp11-kit.so.0.4.11" /usr/lib/libp11-kit.so.0.4.11 | wc -l
sha256sum "$T/usr/lib/libp11-kit.so.0.4.11" /usr/lib/libp11-kit.so.0.4.11
```

### 修复

```bash
T=$(mktemp -d)
tar -xf /var/cache/pacman/pkg/libp11-kit-0.26.5-1-aarch64.pkg.tar.xz -C "$T"
cp -a /usr/lib/libp11-kit.so.0.4.11 /root/libp11-kit.so.0.4.11.broken-$(date +%s)
install -m755 "$T/usr/lib/libp11-kit.so.0.4.11" /usr/lib/libp11-kit.so.0.4.11
ldconfig
p11-kit list-modules          # 验证
systemctl reset-failed NetworkManager && systemctl start NetworkManager
```

> ⚠️ `pacman -S p11-kit` **重装无效** —— 包已是最新，pacman 直接跳过。
> 用 `--overwrite='*'` 或直接 `install` 覆盖。

## 根因 3（自己引入的）：静态 IP 冲突 + wpa_supplicant 抢占

### 3a. 双网卡用同一个静态 IP

我把 WiFi profile 也写成静态 `192.168.1.100`，但那个 IP 被**本机有线**占了：

```
device (wlan0): IP address 192.168.1.100 cannot be configured because
  it is already in use in the network by host DC:A6:32:0F:17:89
device (wlan0): state change: ip-config -> failed (reason 'ip-config-unavailable')
```

NM 自己检测到冲突并拒绝激活。**双网卡同网段绝不能用同一个静态 IP。**

### 3b. NM 和独立 wpa_supplicant 抢同一个接口

```
device (wlan0): Couldn't initialize supplicant interface:
  GDBus.Error:fi.w1.wpa_supplicant1.UnknownError: wpa_supplicant couldn't grab this interface.
device (wlan0): supplicant interface keeps failing, giving up
```

排查替代方案时我启用了 `wpa_supplicant@wlan0.service`（`ctrl_interface=/run/wpa_supplicant-wlan0`），
它**占着 `wlan0` 不放**，NM 自己拉起的 `/run/wpa_supplicant` 实例抢不到。

```bash
# 修复
systemctl stop wpa_supplicant@wlan0.service && systemctl disable wpa_supplicant@wlan0.service
systemctl stop wpa_supplicant.service
rm -rf /run/wpa_supplicant*
```

## 诊断路径（可复用）

### 1. 崩溃堆栈的 `#0` 行才是元凶

```
#0  libp11-kit.so.0 + 0x133dd0        ← 元凶（执行到这里崩的）
#12 g_module_open_full (libgmodule)   ← 调用者，不是元凶
```

### 2. `ldd` / `pacman -Qkk` / ELF 魔数 **都查不出**内容损坏

| 工具 | 为什么查不出 |
|---|---|
| `ldd` | 只解析符号表能否找到，不读代码段 |
| `pacman -Qkk` | mtree 只比大小/权限/时间戳 |
| `head -c4 \| xxd` | 只验 ELF 魔数 `7f 45 4c 46` |
| **`cmp` vs 缓存包** | ✅ **唯一可靠** |

### 3. 手动跑 wpa_supplicant 验证射频层是否正常

```bash
systemctl stop NetworkManager
wpa_supplicant -i wlan0 -c /etc/wpa_supplicant/wpa_supplicant-wlan0.conf -D nl80211
# 看到 CTRL-EVENT-CONNECTED 就说明 驱动/固件/射频 全正常
```

### 4. 判断 NM 说 "unavailable" 的真实原因

```bash
journalctl -u NetworkManager -b | grep -iE "wlan0|unavailable|supplicant"
nmcli -f GENERAL.STATE,GENERAL.REASON device show wlan0
```

## 教训

1. **`pacman -Qkk` 不是内容校验** —— 这台设备已经栽了 5 次
   （`libLLVM` / `btop` / `qt6-base` / `xray-knife` / 现在 `p11-kit`）
2. **正常 `reboot` 也会造成这种损坏** —— 不需要强制断电
3. **双网卡同网段不能用同一个静态 IP**
4. **NM 与独立 wpa_supplicant 不能同时管一个接口**
5. **备用方案（networkd）验证完要及时清理** —— 别留下抢占资源的服务
6. **随时保证有一条物理独立的带外通道** —— 这次靠 3.5" 屏 + 内置键盘救回来

## 附：全盘扫描结果（`tools/verify-content.py`）

同一台设备上跑完整校验，**发现 123 个文件内容不一致**，分布在 25 个包：

| 类别 | 数量 | 影响 |
|---|---|---|
| `libwacom` 数位板驱动 + `.tablet` | 18 | 无（没用数位板）|
| `linux-api-headers` 内核头文件 | 20 | 无（不编译内核模块）|
| `linux-firmware-*` Atheros/MediaTek/DPAA | 14 | 无（没有这些硬件）|
| `util-linux` 波兰语 man 页 | 20 | 无 |
| `vapoursynth`/`vid.stab`/`x264`/`x265` | 20 | 无（不做视频编码）|
| `glib2` 翻译 `.mo` | 11 | 无 |
| **`icu` 核心库 ×2** | 2 | ⚠️ **很多程序依赖** |
| `glibc` / `openssh` / `pam` / `bash` | 各 1 | ⚠️ 需评估 |
| 其它边缘 | 17 | 视情况 |

**损坏模式统一**：文件大小正确、ELF 魔数正确、但中间被填入大段 `0x00`
（最长连续 **63865 字节**）。也有 `0xFF` 模式（见 p11-kit）。

### 存储介质

```
$ cat /sys/block/mmcblk0/device/name
SDABC              ← 无品牌卡
$ cat /sys/block/mmcblk0/device/manfid
0x00006f           ← 未知厂商 ID
```

**结论：这块 SD 卡在物理层面开始失效。**
`0x00` 大面积填充是 NAND 页写入失败的典型特征 ——
控制器报告写入成功，但实际单元没被编程，读回来是全零。

**软件修复只能治标。** 正确做法是换一张正规品牌的工业级 SD 卡
（SanDisk High Endurance / Samsung PRO Endurance），
并把整个系统重新部署上去。

### 为什么损坏集中在"不常用的文件"

这符合 NAND 磨损的分布规律：**长期不被读取的块的电荷泄漏最严重**。
数位板驱动、波兰语手册、没用到的网卡固件 —— 这些文件从装机起就没被读过一次，
所以它们最先掉数据。常用的库（`libc`、`bash`）因为频繁读取会被控制器
刷新（read-disturb 管理），反而更"新鲜"。

**这也解释了为什么损坏能潜伏很久不被发现** —— 你从来不用波兰语 man 页。
