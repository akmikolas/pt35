# Frank-Pi 图形界面无法加载：libvulkan 库被清零

> **Note on redaction.** This document was written while debugging a real device.
> All credentials, subscription URLs, hostnames and addresses have been replaced
> with placeholders (`192.168.1.100`, `MyWiFi`, `user@device`, `YOUR_PASSWORD`).
> Substitute your own values. The technical content is unchanged.

---


**日期**：2026-10-12
**现象**：PocketTerm35 开机后**图形界面完全起不来**（无桌面、无面板），但 SSH 可正常登录
**根因**：`libvulkan.so.1.4.309` 文件内容**被全部清零**（大小正确、数据全 0x00），
导致 `labwc` 无法加载 → greeter 起不来 → `lightdm` 退出码 1 循环重启直至被 systemd 放弃
**状态**：✅ 已修复并验证（重装 `libvulkan1` 单包）

---

## 一、故障链（自下而上）

```
/usr/lib/aarch64-linux-gnu/libvulkan.so.1.4.309 内容全 0x00（592496 字节的零）
        ↓
labwc 加载失败: "invalid ELF header"
        ↓
lightdm greeter 会话 (/usr/bin/labwc) 起不来
        ↓
lightdm 主进程退出码 1 → systemd 快速重启 6 次
        ↓
"Start request repeated too quickly" → lightdm.service failed
        ↓
tty1 的 agetty --autologin frank 也没有拉起合成器
        ↓
【现象】整机无任何图形进程（labwc/wf-panel-pi/Xwayland 全无）
```

## 二、定位过程（关键证据）

| 步骤 | 命令 | 得到的证据 |
|---|---|---|
| 1 | `ps aux \| grep -E "labwc\|Xorg\|wayland"` | **空** → 确认没有任何合成器 |
| 2 | `systemctl --failed` | `lightdm.service` failed、`plymouth-quit` failed |
| 3 | `journalctl -u lightdm` | `status=1/FAILURE`，重启 6 次后 `Start request repeated too quickly` |
| 4 | **`tail /var/log/lightdm/seat0-greeter.log`** | **决定性一行**：`/usr/bin/labwc: error while loading shared libraries: /lib/aarch64-linux-gnu/libvulkan.so.1: invalid ELF header` |
| 5 | `od -An -tx1 -N4 libvulkan.so.1.4.309` | `00 00 00 00`（合法 ELF 应为 `7f 45 4c 46`）|
| 6 | `dpkg --verify libvulkan1` | `??5??????  /usr/lib/.../libvulkan.so.1.4.309`（md5 不符）|

> **为什么 lightdm 的 journal 里没有直接线索**：报错在 **greeter 的会话日志**里
> （`/var/log/lightdm/seat0-greeter.log`），而不是 lightdm 主进程日志。
> lightdm 只报了一个含糊的 `instance with invalid (NULL) class pointer`。
> **这类"库损坏"问题的定位捷径是直接看 greeter/session 日志，而不是主服务日志。**

**迷惑点**：`ls -l` 显示大小正确（592496 字节），所以"文件不存在/被截断"的常规直觉不成立；
必须比对**内容**（magic/od/dpkg --verify）才能发现。

## 三、修复（单包重装，零副作用）

```bash
# 1) 先备份损坏文件用于取证（可选）
sudo cp -a /usr/lib/aarch64-linux-gnu/libvulkan.so.1.4.309 \
           /root/libvulkan.so.1.4.309.corrupt-$(date +%Y%m%d-%H%M%S)

# 2) 重装这一个包
sudo apt-get install --reinstall -y libvulkan1

# 3) 复位失败状态并启动图形界面
sudo systemctl reset-failed lightdm
sudo systemctl start lightdm
```

**验证**：

```
magic:          00000000 → 7f454c46  ✅
dpkg --verify:  ??5?????? → 无差异     ✅
labwc --version: labwc 0.20.2 (+xwayland +nls +rsvg +libsfdo) wlroots-0.20.2  ✅
lightdm:        failed → active (running)  ✅
图形进程:        无 → labwc + wf-panel-pi + pcmanfm + Xwayland  ✅
会话:           Type=wayland Class=user Active=yes  ✅
HDMI-A-1:       connected  ✅        /dev/fb0: 640,480  ✅
```

**注意**：`/var/log/lightdm/seat0-greeter.log` 里仍留有**修复前**的旧报错行，
那是历史日志、不是新故障——不要被它误导。

## 四、为什么会损坏（分析）

| 假设 | 证据 | 判断 |
|---|---|---|
| SD 卡/文件系统故障 | dmesg 中 IO/FS 错误 **0 条**；无 ext4 只读重挂载；空间充足（17%）；系统目录中**没有其它被清零的文件**；图形栈 6 个关键库 ELF 头全部正常 | ❌ **不支持**（但无法排除早期一次性坏块）|
| 镜像构建/烧录时该文件写坏 | 文件 mtime 为 `2025-03-18`，与包内文件日期一致；系统是 2026-10-06 烧录的镜像 | ⚠️ **可能性最大** |
| 运行中被写入清零 | 无相关日志、无掉电记录 | ⚠️ 无法证实 |

**特征**：文件**大小正确、内容全零**，这是典型的"写入了稀疏/零填充数据"，
而不是"文件缺失"或"被截断"。debsums/dpkg 无法区分，只能靠内容校验发现。

> **留档说明**：本仓库另一份文档记录过这个套件/卡的历史——
> 那次是**另一张 microSD 物理损坏**（[ton-technotes ZERO 计划 Part 3]）。
> **本次与那次无关**，本次这张卡（CID 出厂 2024-10）目前健康。

## 五、后续建议

| 优先级 | 项 |
|---|---|
| 🟡 中 | **周期性做包完整性校验**，及早发现类似"内容被清零"的文件：`sudo debsums -s 2>/dev/null \| head`（需装 `debsums`）；或 `sudo dpkg --verify \| head`（较慢，建议只对关键目录跑）|
| 🟡 中 | **加一重图形栈自检**：开机后检查 `systemctl is-active lightdm`，失败则把 `seat0-greeter.log` 尾部写进 `/boot/firmware/` 便于无屏排查 |
| 🟢 低 | 若同一文件**再次**被清零，则高度怀疑存储介质，届时换卡（并用 `badblocks -sv` 或 `fsck -f` 验证）|
| 🟢 低 | 记录本次修复：已备份损坏文件在 `/root/libvulkan.so.1.4.309.corrupt-20261012-223037`，可用于对比分析 |

## 六、无屏设备的排查方法论（可复用）

本次是**掌机无桌面**场景，几点经验值得固化：

1. **SSH 通 ≠ 系统健康**：先分清是"系统没起来"还是"图形层没起来"。
   `ps aux | grep -E "labwc|Xorg|wayland"` 一眼区分。
2. **看单元状态而不是猜**：`systemctl --failed` 直接给出 `lightdm`，
   再用 `systemctl status` 拿到退出码与重启次数。
3. **会话级日志常常才是真相**：greeter/session 的 stdout 落在
   `/var/log/lightdm/*.log`，主服务 journal 里只有含糊错误。
4. **"文件在、大小对"不等于文件好**：判断二进制是否可用要看
   `file`、`od -An -tx1 -N4`（ELF magic）、`dpkg --verify`。
5. **修完立刻验证到最上层**：不是"包重装成功"就结束，要看到
   `lightdm active` + 合成器进程 + `HDMI status=connected` + `/dev/fb0` 尺寸是否正确。

## 七、附：把发布版部署回设备时踩的两个坑

修复图形界面后，顺手把发布版的**英文版代码**同步回设备，过程中踩了两个坑，都值得固化：

### 坑 A：直接 `install` 发布版的 service 模板 → `status=217/USER`

发布仓库里的 `pt35-buttonmap.service` 含**占位符** `User=__PT35_USER__`
（由 `install.sh` 在安装时替换）。我图快直接
`install -m 0644 pt35-buttonmap.service /etc/systemd/system/`，结果 systemd 把
`__PT35_USER__` 当用户名去找：

```
Failed to determine user credentials: No such process
Failed at step USER spawning /usr/bin/python3: No such process
Main process exited, code=exit, status=217/USER      ← 反复重启
```

**教训**：带占位符的模板**永远只能通过安装脚本部署**，不能手工 `install`。
（代码本身没问题——手动前台运行完全正常，这个对照很关键：
**"手工跑得起来、systemd 跑不起来"几乎总是指向单元文件/用户/环境问题，而不是代码问题。**）

### 坑 B：`scp` 对已存在且权限更严的文件会**静默跳过上传**

`/root/pt35-src/install.sh` 权限是 `-rwx--x--x`，`scp` 覆盖时**没有报错但也没更新**，
于是我执行的是**旧版中文安装器**（输出全中文、且逻辑会把服务装成 `User=root`）。
判据：安装输出语言与预期不符 → 立刻怀疑"跑的不是我想的那份文件"。

**教训**：覆盖式上传前先 `rm -f`，或上传后用**内容特征**（行数/哈希/语言）核对，
不要只看退出码。
